Technical analysis · September 2026

Artiest

A drawing app for the Wacom MovinkPad 11. The whole design hangs on one number — the delay between pen tip and wet ink — and Android has a specific, non-obvious API stack for winning it. Everything else is layers, brushes, and file plumbing built around that constraint.

This document was written before a line of code existed. Phase 1 has now been built and measured on the tablet, and the notes marked below are the places where the hardware disagreed with it. Nothing has been deleted: a design document that quietly edits away its wrong predictions stops being evidence of how the decisions were made.

Three of its claims did not survive contact with the device, and all three are load-bearing. There is no front buffer on this hardware (§02.01). The pen has no eraser end and AXIS_DISTANCE is dead, which removes both of §03's palm-rejection mechanisms. An app cannot pin this panel to 90 Hz (§02.06). Motion prediction was built, measured and rejected (§02.02).

The thesis held. The number the design hangs on is now known: 45 ms from pen tip to photons, of which 9.3 ms is the app and 36 ms is SurfaceFlinger and the panel. See docs/phase1-plan.md for the work items, the measurements and the reasoning behind each correction.

01

The device

Confirmed: the Wacom MovinkPad 11 (DTH-A116) — the standalone Android 14 tablet, not the Movink 11 pen display that needs a host computer. The two share a name and demand completely different architectures, so it was worth pinning down. With it settled, Artiest is an ordinary Android app on ordinary Android hardware and the external-display problem never arises.

The hardware suits this well. The EMR digitizer reports 8192 pressure levels and ±60° of tilt — far more headroom than expressive brushes need, so your response curves will be the limit, not the sensor. The panel runs 60 or 90 Hz, and pinning it to 90 removes a third of every frame-bound stage in the latency chain.

8 GB of RAM is the quietly important number. At a 3000×2000 working canvas a layer costs 24 MB, so a full stack sits in memory comfortably and the tile system that would normally dominate a design like this isn’t needed. That deletes an entire subsystem from v1.

Wacom hasn’t published the SoC, so GPU fill rate is the one hardware unknown left standing. Phase 0 measures it.

Measured · Phase 0 and W2

MediaTek MT8781V/NA, Mali-G57 MC2, GL ES 3.2, GL_MAX_TEXTURE_SIZE 16383. Fill rate was never the constraint. A full redraw with the layer live as a rotating texture measured p99 4.00 ms against an 11.1 ms budget, 0% dropped over 600 frames — because the per-frame blit is destination-bound on the 2.6 Mpx surface, not on the 7.1 Mpx document. Memory came in at 7.70 GiB total, 4.4 GiB free, and the peak Phase 1 graphics footprint is about 121 MiB.

One correction in the paragraph above: “pinning it to 90” is not something an app on this device can do. See §02.06.

02

Latency is the whole game

"Very little delay" is the requirement that constrains every other decision — it rules out the obvious UI framework for the canvas, dictates the rendering path, and sits in direct conflict with stabilization. Android has first-party APIs for this. Use all of them.

  1. 01 Front-buffered rendering biggest win androidx.graphics:graphics-core → GLFrontBufferedRenderer. Draws the in-progress stroke segment straight into the front buffer, skipping the normal double-buffer and compositor path. Implement onDrawFrontBufferedLayer() for wet ink and onDrawMultiDoubleBufferedLayer() for the committed scene; call commit() on pen-up. Requires API 29+.
    Refuted on hardware · W0, priced at W16

    This device has no front buffer. W0 put graphics-core's own question to gralloc — its exact usage set (4294970112) and, separately, the bare USAGE_FRONT_BUFFER bit — and both were refused. CanvasFrontBufferedRenderer has therefore always run its fallback path: same SurfaceControl, same hardcoded 1000 fps frame-rate vote, no exception, no log line, and no API to ask afterwards which it got. Nothing about the code looks different when this happens.

    It is still what Phase 1 ships, on the only criterion the phase has: judged by eye at a verified 90 Hz against a hand-built SurfaceControl arm and a plain-View baseline, its ink sat closest to the pen. Both other arms read as smoother but further behind. So the library won without the mechanism this entry credits it with, and why it wins is still unverified — it becomes a real question in Phase 2, when a GL engine has to reproduce the win without it.

    W16 prices the difference. Of 45 ms pen-to-photon, 36 ms is SurfaceFlinger and the panel — 3.2 refreshes at 90 Hz — which is precisely the path this entry says is skipped. Four fifths of the latency is downstream of the app.

    Two smaller corrections: the committed-scene callback is onDrawMultiBufferedLayer(), and Phase 1 uses the Canvas renderer rather than GLFrontBufferedRenderer — GL is Phase 2's, and recorded as debt rather than oversight, because Phase 1's whole render is antialiased circles plus one matrixed bitmap blit and hardware Canvas already does both on the GPU.
  2. 02 Motion prediction androidx.input:input-motionprediction → MotionEventPredictor. Feed it every event with record(), call predict() on each move, and render the predicted point as temporary ink only. Clamp prediction distance or fast direction changes overshoot visibly.
    Built, measured, rejected · W11 and W16

    The warning in this entry is right and the mitigation is not enough. “Render the predicted point as temporary ink only” assumes ink that can be taken back. On this render path it cannot: the front-buffered layer accumulates, so a speculative dab is baked until pen-up. Clamping the distance reduces how far the overshoot goes; it cannot erase the overshoot that happens.

    Under a real pen the result is visible and stays visible — jagged sections along the wet stroke that persist until the pen lifts, then vanish, because the committed stroke is rebuilt from real samples alone. The layer was always clean; the screen was not.

    The measurements, for the record: MotionEventPredictor.newInstance resolves to SystemMotionEventPredictor, and MotionPredictor.isPredictionAvailable returns false for this pen's device id and source — and it predicts anyway, a mean 41.5 and a maximum 110 document px ahead of the last real sample, about 27 ms of lookahead. It costs 3× the per-event time and 11× the allocation, and produces as many speculative dabs as real ones. It ships behind a toggle, defaulting off.

    The blocker is the render path, not the predictor. An engine that re-renders the wet stroke each frame makes every spur erasable, and at that point prediction is worth re-testing against the 5.75 ms of digitizer-and-dispatch lag it exists to hide.
  3. 03 Unbuffered dispatch view.requestUnbufferedDispatch(event) on ACTION_DOWN. Stops Android batching motion events to the frame boundary so samples arrive as the digitizer produces them.
    Confirmed, with a caveat · Phase 0

    It works: 1.14–1.19 samples an event at 218–271 events a second, far above the panel. But 4–6% of events still carry 2–4 historical samples, so the next entry stays mandatory rather than becoming an optimisation. The MotionEvent overload is used, so the request lasts for the gesture and not for one event.
  4. 04 Historical samples The EMR digitizer samples far faster than the panel refreshes. Iterate getHistoricalX/Y/Pressure(i) before the current point on every event — skipping history throws away most of your resolution and gives visibly faceted curves.
  5. 05 Keep Compose off the canvas Compose recomposition plus its draw pipeline adds latency you cannot claw back. Canvas is a SurfaceView. Compose is excellent for panels, layer lists, and toolbars — just not for ink.
  6. 06 Request 90 Hz The panel does 60 and 90. Pin the highest mode via Surface.setFrameRate() / preferred display mode — it cuts a third off every frame-bound stage in the chain.
    Refuted on hardware · W15

    An app cannot pin this panel to 90 Hz. Wacom's /vendor/etc/displayconfig/display_id_0.xml sets mDefaultPeakRefreshRate to 61 with mAlwaysRespectAppRequest: false, so a preferredDisplayModeId asking for 90 reaches SurfaceFlinger, is recorded, and loses to the user-setting vote. 90 Hz needs adb shell settings put system peak_refresh_rate 90.0 and min_refresh_rate as well — every measurement in this project that says 90 Hz was taken with that override live and verified in dumpsys display.

    Two traps that cost real time. The override lapses on its own, and settings get keeps reporting 90.0 while the live vote is capped at 60 — only the vote is the panel. And starting an activity drops it, so it has to be re-bounced (60.0, then 90.0 — writing 90 over 90 fires no observer) after the app is on screen, and verified again afterwards.

    What the app can always do is ask for something lower: an app's base-mode request beats the user's minimum vote, which is how a genuine 60 Hz control was built without touching device settings between runs. One more caveat on “pin the highest mode”: a Display.Mode carries a physical size as well as a rate, so picking the fastest one can ask the compositor to change the panel resolution. On a drawing app that is the pen and the ink landing in different places.

    The claim about what it buys is confirmed and larger than stated: the digitizer rate tracks the panel — 246.85 Hz at 60, 321.75 Hz at 90 — so the override buys input rate as well as frame rate.
Direct conflict in your spec

Stabilization is deliberately added latency. A pulled-string stabilizer works by holding the rendered point behind the true pen position — that is what makes the line smooth. So "stabilization" and "very little delay" pull against each other by definition.

Resolution: expose it as a 0–100 slider that genuinely reaches zero, default it low (~15), and set it per-brush — high on inking pens, near-zero on sketch pencils. Don't bake a fixed amount into the pipeline.

Confirmed and quantified · W7 and W16

Shipped as written: a slider reaching a bit-exact zero, defaulting to 0.15, living on the brush. The conflict now has a price. On a steady line the filter settles 4.58 ms behind the pen at 321.75 Hz (4.20 at 246.85) — and that is not its time constant, which is 6.0 ms: the filter is evaluated at sample instants, so the exact discrete lag is dt·q/(1−q) with q = exp(−dt/τ), about τ − dt/2. Getting that wrong would have the latency film subtracting a quarter more smoothing than the smoothing does.

Against a 45 ms total, the default costs about a tenth — and more than the entire rest of the software path put together. The filter integrates over each sample's dt rather than lerping per sample, so its feel does not change with the refresh rate; a per-sample lerp would have changed the line by a third between 60 and 90 Hz.

And the cost depends on what you are drawing. A first-order lag delays a corner by about 0.6 τ rather than τ — the continuous limit is ln 2 — so the same default that costs 4.58 ms on a straight stroke costs 2.79 ms at a reversal. A filmed A/B at 90 Hz could not separate it from zero, which is the correct outcome: 2.8 ms is inside that instrument's resolution, and the filter is measured exactly by a unit test instead.

03

Input pipeline

One path from digitizer to GPU. Every stage is testable in isolation, and the source is abstracted so a desktop mouse, a finger, and the Pro Pen 3 all feed the same code.

MotionEvent+ history → InputSample→ predict→ stabilize→ spline fit→ resample by spacing→ stamp→ GL

InputSample carries x, y, pressure, tilt, orientation, distance, timestampNanos, toolType. Normalize once at the boundary; nothing downstream should touch a MotionEvent.

  • Pressure. AXIS_PRESSURE arrives normalized 0–1 as a float, so the pen's 8192 levels survive the trip. Raw linear pressure feels terrible — ship a per-brush response curve (an editable cubic) mapping pressure to size and opacity independently.
  • Tilt & orientation. AXIS_TILT (0–π/2) and AXIS_ORIENTATION (±π). These are what make a pencil shade broadly when you lay it over — the single biggest driver of "this feels like a real pencil".
  • Eraser end. Flipping the pen reports TOOL_TYPE_ERASER. Route it to the eraser tool automatically and remember the last eraser brush.
  • Palm rejection. Handle ACTION_CANCEL and, on Android 13+, per-pointer FLAG_CANCELED — both mean discard the entire stroke back to its ACTION_DOWN. Also suppress finger input on the canvas while AXIS_DISTANCE shows the pen hovering.
  • Barrel buttons. getButtonState() — map to user-assignable actions (colour picker, pan, undo).
Both palm-rejection mechanisms refuted · Phase 0 and W4

The pen has no eraser end. Flipping it reports TOOL_TYPE_FINGER, never TOOL_TYPE_ERASER. That is not merely absent but actively unusable, because FINGER is the one bucket palm rejection exists to discard — so flip-to-erase would be routed to the eraser only by breaking the thing above it. Eraser becomes a barrel-button mapping; all three buttons are individually addressable (BUTTON_TERTIARY 4, BUTTON_STYLUS_PRIMARY 32, BUTTON_STYLUS_SECONDARY 64).

AXIS_DISTANCE is dead on this digitizer. 400 hover samples captured through a demonstrably working onHoverEvent/getAxisValue path, every one reporting 0.0. Hover-height finger suppression cannot be built as written, and it is deleted rather than deferred. InputSample still carries the field; it is always zero.

What replaced them is an explicit state machine rather than a heuristic: a gesture takes two fingers, lone fingers are dropped entirely, and the pen wins — a palm landing before the pen no longer locks the pen out, and a pen arriving mid-gesture is refused rather than mixed in. Eight contact sequences are replayed through the real view on the device as a regression check. ACTION_CANCEL and FLAG_CANCELED are both handled and counted; FLAG_CANCELED has never once been observed from this driver, which is worth reading as “not yet” rather than “never”.

04

The one architectural fork

Google shipped androidx.ink — a Jetpack library with brushes, stroke geometry and a live-authoring path tuned for exactly this. With vector layers deferred to v2, the calculus shifts: Ink’s strongest card no longer applies to v1.

A. Ink API for everything fastest

Strokes, brushes, low-latency authoring and geometry ops all provided. Something good-feeling in weeks rather than months.

Ceiling: its brush families are built for note-taking — pen, marker, highlighter. Textured graphite and felt bleed are not what it is for, and raster layers aren’t its model at all.

B. Custom GL engine recommended for v1

Full command of stamp textures, grain, blend modes and accumulation — the only route to a pencil that reads as graphite.

Cost: you rebuild live authoring and prediction integration yourself. Vector geometry was the other half of that cost, and deferring vector removes it.

C. Hybrid v2

Custom GL for raster, Ink API for vector layers when they arrive. Its Stroke model plus the geometry module is what makes vector erase and selection tractable.

Cost: compositing two render paths into one canvas — real, but deferred along with vector itself.

Deferring vector inverts the recommendation I’d have made otherwise, and it’s worth being explicit about why. Ink’s headline advantage was handing you vector strokes and geometry nearly free — the hardest item on the original list. Take that out of v1 and what remains is a raster painting app whose defining quality is brush feel, which is precisely where Ink’s ceiling sits. So the custom GL stamp engine becomes the v1 engine, and Ink returns in v2 for the vector layer.

This is not the same as starting from scratch

Use the Ink API and Google’s low-latency-stylus sample as your Phase 0 and 1 spike. They put ink on screen in days, prove the hardware chain, and hand you a latency baseline to measure your own engine against. Treat that code as a measuring instrument rather than a foundation — the real engine starts in Phase 2.

One check that could flip this

Ink’s API surface has moved fast, and custom textured brushes were still experimental as of my information. If texture support in BrushFamily has properly landed, option A stretches much further than I’m crediting it and could carry v1 alone. Read the current androidx.ink release notes during Phase 0 — a ten-minute check that could save a month.

Answered 2026-09-08 · the check flipped, the recommendation did not

The check was finally run at the top of Phase 2, and this paragraph's condition is met. Phase 1 cut the timeboxed arm, so the question stood open through the whole phase. Read now: androidx.ink 1.0.0 is stable, 1.1.0-alpha03 made the programmatic brush-customisation API public and split BrushPaint.TextureLayer into specific subclasses, 1.1.0-alpha06 improved the protobuf representation of custom texture layers, and TextureBitmapStore exists. So texture support in BrushFamily has properly landed, and by the test written above, option A stretches further than this document credited.

The recommendation survives it anyway, for reasons this document could not have known. Ink replaces one raster layer with a list of immutable strokes — a different memory model, undo model and export path, which now means discarding five shipped Phase 1 work items rather than swapping a brush. InProgressStrokesView sits on the same androidx.graphics stack on the same device with no front buffer, so it inherits the identical 36 ms and offers no latency win. And custom brushes are authored through @OptIn(ExperimentalInkCustomBrushApi::class) and shipped as gzipped protobufs that cannot be read or diffed. Recorded in docs/phase2-plan.md, together with the kill criterion this paragraph implies: if the custom engine ships texture and scatter and the pencil still reads as a grey pen, fall back to Ink for v1.

What did change is the price of the recommendation. The custom engine is still right for v1, and Phase 1 shipped raster ink without it — but W16 measured where the latency actually lives, and 36 of 45 ms is the compositor, not the engine. A GL engine is worth building for brush feel, and for a wet layer that can be re-rendered — which is what would make prediction usable. It is not where the remaining latency is, and expecting it to be would be planning against the wrong number.

05

Prior art worth reading

You're right that this shouldn't be built from scratch. But the valuable prior art is mostly not what a "Kotlin drawing app" search returns — those are overwhelmingly tutorial projects: a Canvas, a Path, a colour picker, no pressure model, no layer compositing, no latency work. Your read on the quality is correct. What's actually worth your time splits into three tiers, and the licence differences between them matter more than the code does.

Tier 1 — the brush engine highest value

libmypaint (C, ISC licence). The reference implementation of precisely the model in section 07: inputs — pressure, speed, direction, tilt, random — mapped through user-editable curves onto outputs like radius, opacity, hardness and dab offset. Its brushsettings.json is a readable specification of every parameter, which is a shortcut past weeks of design work. Used by MyPaint, GIMP, OpenToonz and Krita. ISC is permissive, so you can port the model or link the C library through the NDK with no licence constraint on Artiest.

Krita (C++/Qt, GPL). The best-documented layer stack, compositing and blend-mode implementation in open source. Read it for architecture — GPL means you study the design, not lift the code.

Tier 2 — the Android plumbing

chromeos/low-latency-stylus — Google's official front-buffered stylus demo. This is section 02 as working code; it's where Phase 0 should start rather than from a blank project.

Cahier — a 2025 official Android sample for large-screen creative apps, built on the Ink API. The closest thing to a reference implementation of the modern stack.

Ink API samples — AOSP's, plus community ones such as NicosNicolaou16/Ink_Api_Compose (stroke rendering, erase, stroke-to-bitmap, persistence). The fastest way to judge the Ink API's brush ceiling from section 04 before committing to it.

Tier 3 — formats and interop

OpenRaster spec (freedesktop) — the .ora format from section 09, small enough to implement in a day.

MyPaint .myb brushes — if you port the libmypaint model, thousands of existing community brushes become importable. That is enormous leverage for a one-person project, and it turns brush authoring from a task into a download.

Licensing, simplified — because this is a personal tool

Krita, GIMP and MyPaint-the-application are GPL; libmypaint is ISC. That distinction governs distribution, not use — GPL obligations attach when you ship code to someone else. A tool you build and run yourself can borrow freely from any of them, which widens the useful prior art considerably.

The one line to watch: your repo is private, and that is what keeps the above true. Publishing it would count as distribution, and any GPL-derived code in it would then oblige you to license Artiest under the GPL as well. Decide once now — keep it private, or keep GPL code out — rather than discovering the constraint later.

Brush tip and grain textures follow the same logic: for a personal tool, source whatever works. Provenance only starts to matter if Artiest ever goes public, and a NOTICE file kept as you go costs far less than reconstructing one afterwards.

06

Layers & compositing

Each bitmap layer is a GL texture, RGBA8 premultiplied. With 4096×4096 fixed as a hard ceiling, a full-size layer costs exactly 64 MiB and the arithmetic stays comfortable at 8 GB of RAM. Tiling is off the table entirely — not deferred to v2, simply not needed. That removes the single largest subsystem a design like this normally carries, along with its cache eviction, dirty-region tracking and compressed-tile storage.

Enforce the ceiling as a texture memory budget rather than a layer count, so small canvases aren't punished for the limit that exists to protect large ones. Roughly 1.5 GB of layer textures gives about 24 layers at full 4096² size, ~96 at 2048², and effectively no limit at sketch sizes. Show the budget in the layer panel and refuse the add rather than letting the GPU fail an allocation mid-stroke.

Compositing the full stack on every frame is wasteful. Cache the flattened result of everything below the active layer and everything above it, leaving three textures to blend while drawing. Rebuild the caches only when the stack changes.

The detail that makes strokes look right

Stamping directly onto the layer with alpha blending produces dark blobs wherever a stroke crosses itself — slow curves, loops, hatching. Every stamp re-blends over the last.

Instead: render the whole in-progress stroke into a scratch FBO at full opacity, then composite that buffer onto the layer once at the brush's opacity. Uniform density across the stroke, matching what Clip Studio and Photoshop do. Wet ink shows the scratch buffer; commit() does the real composite.

Layer operations are the easy half: add, rename, delete, reorder, visibility, opacity, and blend mode. Ship Normal and Multiply in v1 — that covers sketch-under-ink workflow, which is what a reference-driven artist actually needs. Add, Screen, and Overlay can follow.

07

Brush engine

Stamp-based, which is how every raster brush you've used works. Fit a Catmull-Rom spline through the smoothed samples, resample it at fixed spacing (a fraction of brush size), and at each point stamp a textured quad — scaled by pressure, rotated by tilt or direction, tinted by colour.

Make the brush a serializable data model, not code. One JSON-backed struct drives all three of your brushes and every one you add later:

Brush {
  tipTexture, spacing, sizeMin, sizeMax, hardness,
  pressure→size curve, pressure→opacity curve, tilt→size curve,
  flow, opacity, blendMode,
  grainTexture, grainScale, grainDepth,
  angleJitter, sizeJitter, positionJitter,
  stabilization, antiAlias
}

Sketch pencil

Grain texture sampled in canvas space, not stroke space, so the paper tooth stays fixed as you scribble across it. Pressure drives opacity more than size; tilt widens the stamp for shading. Low flow so it builds.

Pen

Hard-edged round tip, full opacity, pressure drives size only. Anti-aliasing matters most here — use an SDF tip with analytic coverage rather than a texture, so edges stay clean at any zoom.

Felt marker

Soft-edged stamp, multiply blend, flat opacity within a stroke but building where strokes overlap. Slight tilt-driven width for the chisel feel.

Your anti-aliasing toggle should switch stamping between smooth alpha coverage and nearest-neighbour with an alpha threshold — the latter for crisp pixel work. And the eraser is not a separate tool: it is any brush rendered with destination-out blending, which means it inherits pressure, texture, and stabilization for free.

08

Undo & redo

Cheap to describe, expensive to get wrong — it constrains the memory model, so design it alongside layers rather than bolting it on.

Command pattern with a bounded stack. The trick is that different operations need completely different storage strategies:

  • Bitmap strokes — snapshot only the dirty rect's before-pixels, not the layer. A typical stroke touches a small fraction of the canvas, so entries stay small. Compress with LZ4 if memory gets tight.
  • Vector strokes — an object add/remove diff. Essentially free, which is a real argument for the Ink API path.
  • Layer metadata (rename, opacity, reorder, visibility) — trivial property diffs.
  • Layer delete — keep the texture alive in a limbo pool rather than copying it out; drop it when the entry is evicted.
  • Image import — hold a reference to the decoded bitmap.

Coalesce aggressively: one entry per completed stroke, never per stamp. Cap the stack by both depth (~60) and total bytes (~512 MB), evicting oldest first. Clear the redo branch on any new action after an undo. Persisting undo across app restarts is a nice-to-have — skip it in v1.

Give it a real UI presence: undo and redo belong in the always-visible chrome, not a menu, and both should be assignable to the pen's barrel buttons.

09

Files, import & export

Android 14 is fully scoped-storage: WRITE_EXTERNAL_STORAGE does nothing. The good news is the modern replacements need no runtime permissions at all.

  • Export to the tablet's gallery — write through MediaStore.Images into Pictures/Artiest/. Files land locally, appear in the gallery immediately, no permission prompt. This is your default "Save as PNG/JPG".
  • Export anywhere else — SAF ACTION_CREATE_DOCUMENT for a user-chosen folder.
  • Import an image as a layer — the Photo Picker (PickVisualMedia). Zero permissions, system-provided UI, and the user only exposes the one file they chose. Decode with ImageDecoder, downsample to canvas size, insert as a new layer. Perfect for reference images.
  • Project format — use OpenRaster (.ora) rather than inventing one. It's a ZIP with stack.xml, a PNG per layer, and a merged preview; Krita and GIMP open it. The spec tolerates extra files, so tuck your vector-layer JSON and brush references inside the same archive.
  • Autosave — periodically and on onStop(), with crash recovery on launch. Non-negotiable in an art app; losing an hour of drawing is unforgivable.
10

Customizable toolbars

Build a tool registry from the start: every action is an entry with a stable ID, icon, label, and optional parameter panel. Toolbars then become a serialized list of IDs, stored in Proto DataStore, and customization is just editing that list.

Long-press enters edit mode; drag to reorder, add, or remove. Support docking left or right — a right-handed artist wants tools out from under their hand, and this is the accessibility win people notice most on a pen tablet. Always keep "reset to default" reachable. In Compose this is a LazyRow/LazyColumn plus detectDragGesturesAfterLongPress.

The colour wheel is a custom Compose canvas: HSV ring with an inner triangle or square, plus hex entry, a recent-colours strip, and a saved palette. Make it dismissible and repositionable — screen space on an 11" tablet is the scarce resource.

Build sequence

Ordered so the riskiest unknown is settled in week one and every phase after it produces something you can actually draw with.

Not an app — a logging harness. Dump every MotionEvent field the Pro Pen 3 produces: pressure range and quantization, tilt, orientation, hover distance, sample rate, tool types, button state. Then film the screen at 240 fps and count frames from tip movement to ink.

Four more were opened by the build, and this is where they stand.

✓

What the latency actually is: 45 ms, pen to photons.9.3 ms of it is the app — 5.75 digitizer and dispatch, 3.21 the spline, 0.31 the app's own work — and 36 ms is SurfaceFlinger and the panel, 3.2 refreshes at 90 Hz. Measured from a 240 fps film of a zigzag, four reversals agreeing within 4 ms, with the capture rate calibrated against the panel's own refresh visible in the ink.

✓

Whether the front-buffer path exists here: it does not.And the library was shipped anyway, because it still felt closest to the pen. Why it wins is unverified and becomes load-bearing in Phase 2, when a GL engine has to reproduce the win without it.

✓

Whether textured brushes have landed in androidx.ink: they have.1.0.0 is stable, the brush-customisation API went public in 1.1.0-alpha03, and texture layers are real. The check this document asked for was run at the top of Phase 2 and it flipped — and the recommendation held regardless, because Ink’s cost is the document model and its benefit is not latency. See §04.
